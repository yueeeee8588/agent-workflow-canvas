# Agent Workflow Canvas (多 Agent 工作流画布 · 快捷回复回传架构版 V2.4.1)

## 2.4.1 必要权限修正

依据当前运行宿主 1.0.16-beta 的 `APPS.md`「卡片回传（hana.emit）」：应用卡回传唤醒 Agent 必须声明并获得 `app/session.start-turn`。2.4.0 误将这项能力与旧总线会话管理能力一起删除；2.4.1 补回该能力并将其加入回归断言。仍不声明 `app/sessions.manage`，仍不注册 `tools/pre-execute` 会话审批锁，也不调用 `session:send/list/get`。

现场已证实批准记录成功保存、未被领取，截图显示 SDK 在 `hana.emit` 阶段等待响应超时。缺少能力是确定缺陷；宿主为何未返回明确拒绝仍未证实。该修正不宣称超时根因全部解决，需要真实用户点击联合验收。不得自动重发已有批准事件，尤其用户仅为展示测试而生成的业务画布。


> **版本定位**：为 HanaAgent 设计的标准多 Agent 协作工作流画布应用（manifestVersion: 2）。
> 采用**快捷回复卡片回传架构**与**可信后端审批凭据核销机制**，生成卡片立即呈现，经由认证 UI API 持久化方案审批凭证，并通过宿主原生事件无 `to` 回传与模型工具安全领取。

## 🌟 核心架构与设计原则

1. **生成卡片立即返回 (出图即待批)**：
   - 面对多步骤工程、跨模块改动或需要派发分身的复杂任务，调用 `render_workflow` 后立即生成卡片并交回用户，出图即待批；
   - 移除旧版对 `sessionId` / `sessionPath` 反查的硬绑定，无会话身份时依然正常出图呈现。
2. **完整 DAG 拓扑分层与并发写冲突防护**：
   - 100% 保留显式 `dependsOn` 拓扑分层、循环依赖检测、自依赖拦截与前序全依赖兼容转换；
   - 保持基于全局可达性分析的 Shared Write 共享写入资源并发冲突检测与自动安全串行化消解；
   - 保持四重全景滑动导航（悬浮翻页、鼠标抓手 Drag-to-Scroll、滚轮横向映射、宣纸细滑块）。
3. **人员配置与动态专员登记**：
   - 保留各工作包内嵌的专员下拉调换机制，支持从官方全景专员名录中选配；
   - 保留纯 DOM 水墨模态弹窗「➕ 添加自定义助手」，动态登记新 ID 并即时同步开放指派。
4. **认证 UI API 凭据持久化与确定性方案指纹 (planHash)**：
   - 用户点击卡片提交时，前端调用 App 认证后端端点 `POST /workflow/:id/execute`（兼容 `/approve`）；
   - 后端对责任人分配执行严格白名单强校验（拦截未知专员与非法节点）；
   - **方案全量指纹计算**：指纹不仅包含责任人、依赖和写目标，更全面涵盖工作流标题、说明、各工作包的具体任务描述、权限边界与验收条件（五要素全量契约），任何字段变异都会改变指纹；
   - **服务端生成 submissionId**：禁止客户端自行指定 submissionId，由服务端基于完整 `randomUUID()` 权威生成；明确定义为公开去重标识，非权限凭据；
   - **已批准方案禁止静默改人**：方案一经批准，若传入不同分配产生不同指纹，服务端直接 409 拦截拒绝；相同指纹支持幂等重试并沿用原 submissionId；
   - **单进程文件系统级原子替换落盘**：使用临时文件 + `renameSync` 原子写入，防止进程崩溃导致残缺文件。
5. **宿主事件回传与手势生命周期保障**：
   - 前端拿到后端持久化凭据后，通过 `hana.emit('workflow.approved', payload)` 或 `window.card.emit('workflow.approved', payload)` 无 `to` 回传，由宿主统一路由；
   - **严格分支鉴别**：`hana.emit` 严格只认可 `{ delivered: true }`；`window.card.emit` 严格只认可 `{ ok: true }`；缺少宿主 bridge 时立即拒绝，绝不伪造成功；
   - **同步手势保障**：异步网络完成后若丢失浏览器手势激活状态，前端按钮提示「🚀 再次点击发送已批准方案」，用户下一次点击在原生点击事件同步调用栈中立即发起 `emit`，保障手势检测通过；
   - **锁定配置防误发**：方案获批后前端物理禁用所有专员下拉框与添加按钮，彻底防止“界面换了新专员却发送旧缓存指纹”的错位；
   - **刷新后允许重发**：用户刷新卡片后，页面检测到已批准状态，按钮恢复为可重发状态，允许重新回传原事件，彻底告别旧版永久锁死按钮的缺陷；
   - **投递语义界定**：`emit` 成功仅表示宿主接受投递，不代表任务已派发或执行完毕。
6. **模型可信核销工具与防重复派发**：
   - 暴露 `get_approved_workflow`：读取真实后端存储的批准方案与恢复状态，动态比对当前存储内容的方案指纹（篡改检测），不信任前端未经验证的 payload；
   - 暴露 `consume_workflow_approval`：原子领取并核销审批凭证，严格校验 `workflowId`、`planHash` 与 `submissionId`；
   - **状态标记契约**：核销仅标记为 `claimed` / `consumed`，绝不标记为 `dispatched` / `executed`（不冒充下游派发与执行终态）；
   - **防重复派发收据**：重复调用时返回 `duplicate: true`、`alreadyConsumed: true` 及已有 receipt，引导下游模型与主控感知到无需重复派发。

## ⚠️ 诚实工程边界说明（必读）

1. **无全会话硬拦截**：
   - 依照用户明确指令（不锁会话），本候选版本已彻底移除旧版 `tools/pre-execute` 钩子黑名单拦截器与跨会话管理权限；
   - 规划仍待用户批准，但本应用在当前架构下**不提供对原生 subagent/write 工具的全会话硬拦截门禁**，不假装 hard gate 被等效保留。
2. **不承诺分布式 Exactly-Once**：
   - 插件层通过状态原子更新与收据比对提供单进程幂等防重保障；但若下游模型在领取凭证后发生网络断流、上下文截断或崩溃，再次调用返回 duplicate 收据；
   - 模型与主控不能盲目重派，必须结合 receipt、真实任务 `taskId` 或人工现场综合核对。
3. **内容指纹为篡改检测，非物理不可修改**：
   - 审批记录持久化存储于本地文件系统，重新读取时通过重新计算全量指纹比对实现防篡改检测（若文件被外部工具修改则报错拒绝）；
   - 文件本身受操作系统文件权限保护，不伪称硬件级或分布式不可篡改。
4. **App UI API 认证现状**：
   - 经审查宿主源码快照（`server/http/route-security.ts`, `request-principal.ts`, `plugin-surface-session.ts`），宿主网关层 `authenticatePluginSurfaceRequest` 会校验卡片 session Header 并限制同 App routes；
   - 本应用自身不额外伪造自制 Header 冒充平台网关防伪；生产环境鉴权依托宿主官方网关，尚待真实宿主环境联合验收。
5. **历史数据迁移限制**：
   - 所有旧版历史工作流数据仍可读；但旧版残留的 `delivery_unknown` 状态记录不可自动重发（直接 423 拒绝），需重新生成画布规划。

## 🛠️ 包含的模型工具 (Tools)

1. `render_workflow`：
   - 协同规划与 DAG 拓扑看板生成工具；出图即待批，生成后立即返回卡片。
2. `get_approved_workflow`：
   - 读取经可信后端持久化批准的工作流全量方案与恢复状态；核验方案指纹。
3. `consume_workflow_approval`：
   - 原子核销已批准方案凭据，标记为 `consumed` 并返回收据；重复调用返回 `duplicate: true`。
